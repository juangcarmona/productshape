# Repository map

ProductShape keeps maintained implementation and publication source beneath `src/`, while canonical product and architecture documentation remains beneath `docs/`.

| Path | Ownership | Lifecycle role |
| --- | --- | --- |
| `docs/` | Product, architecture, operations, adoption and contributor documentation | Canonical human-authored documentation; published or referenced by build tooling |
| `src/packages/` | Workspace packages, CLI, integrations, schemas and package-local assets | Maintained runtime and distributable source; package boundaries and names are stable |
| `src/public-site/` | Astro site shell, locale configuration/content, shared styles, branding and delivered diagram artifacts | Maintained source and checked-in provenance for the public and engineering publication family |
| `src/scripts/` | Repository, publication, release and conformance automation | Maintained supporting tooling invoked by package scripts and CI |
| `tests/` | Unit, integration, conformance, release and publication checks | Maintained verification source; tests may use checked-in fixtures |
| `.archify/` | Archify candidate inputs and workflow receipts | Maintained diagram inputs and generation provenance; outputs remain derived |
| `docs/assets/` | Canonical visual baselines and documentation media | Maintained documentation assets; not a runtime output directory |
| `.product/`, `_site/`, `dist/`, `coverage/` | Generated local or CI output | Disposable; never canonical source and normally ignored |

## Publication boundaries

The public site is built with the Astro project rooted at `src/public-site/`. Its localized content is in `src/public-site/content/`; templates and components are in `src/public-site/src/`; shared styling and brand assets are in `src/public-site/assets/`. The legacy content compiler remains an internal compatibility adapter until all existing page content has been represented by Astro components; Astro owns the final static build and route enumeration.

The engineering publication uses the same Astro project with a different profile and base path. The generated Product Snapshot is copied into the engineering output as a standalone file and remains separately generated by the CLI. It is not rendered by Astro and does not inherit site runtime state.

Mermaid is an authored convenience view. Markdown documents with fenced `mermaid` blocks (and legacy `.mmd` sources) can be rendered to static SVG with `node src/scripts/render-mermaid.mjs --input src/public-site/diagrams --output dist/mermaid`. Archify artifacts are selected explanatory views and must retain their candidate/source links and revision metadata. Neither diagram path is canonical Product Model data.

## Root-level boundaries

The repository root is reserved for project metadata and lifecycle tooling (`package.json`, lockfiles, workspace configuration, CI configuration, contribution guidance and generated-output policy). New maintained source belongs under `src/`, `docs/` or `tests/` according to the table above. A layout test prevents the former root-level `packages/`, `site/` and `scripts/` directories from returning.
