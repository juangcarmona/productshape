# Adopting in an existing OpenSpec repository

This guide is for repositories that already run OpenSpec. Product Definition as Code adds a
product-definition layer above your existing workflow; OpenSpec keeps owning everything it owns
today. This repository itself works exactly this way.

> **Milestone note.** The `product-definition` CLI and the OpenSpec adapter do not exist yet; the
> adapter ships with the `implement-product-change-and-handoff` and
> `package-ai-and-sdd-integrations` changes. The contracts below are fixed in the
> [specification](../specification/handoff-contract.md). See
> [Limitations of v0.1](../limitations-v0.1.md).

## What Product Definition adds

OpenSpec answers "how do we specify, design and verify this implementation increment?". Product
Definition answers the question upstream of that: "what is the product, and what exactly are we
changing about it?". It adds:

- A canonical product model under `docs/product/model` — actors, journeys, use cases, rules,
  terms, contexts, requirements, constraints — compiled into a validated product graph.
- Product Changes: explicit, validated deltas against that model, decomposed into delivery slices.
- Product Handoffs: generated, framework-independent packages of product context, one per delivery
  increment, consumed by your OpenSpec changes.

The flow becomes: Product Definition → Product Change → Delivery Slice → Backlog Item → Product
Handoff → **native OpenSpec workflow** → Implementation → Verification → explicit Promotion.

## What OpenSpec keeps owning

Everything native. The `openspec/` directory, its folder layout, `proposal.md`, `design.md`,
`tasks.md`, spec deltas, the propose/apply/archive lifecycle and its tooling are unchanged.
Product Definition never writes into OpenSpec's own artifacts, never drives its lifecycle, and
OpenSpec never rewrites canonical product knowledge. The boundary is normative: see the
[SDD boundary](../specification/handoff-contract.md#sdd-boundary).

## The sidecar files

When a Product Handoff targets an OpenSpec change, three sidecar files appear inside that change's
directory, next to the native artifacts:

| File                    | Owner                                                           | Nature                                                                                                                 |
| ----------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `product-handoff.yaml`  | Generated by `product-definition handoff create`                | The handoff contract: implemented requirements, affected artifacts, content digests, source revision. Never hand-edit. |
| `product-context.md`    | Generated alongside the handoff                                 | Human- and AI-readable product context for the increment. Non-canonical; regenerated, never edited.                    |
| `product-coverage.yaml` | Adapter-owned traceability, maintained during the OpenSpec work | Maps each implemented requirement to the OpenSpec tasks and verification evidence covering it.                         |

Sidecars are additive. OpenSpec tooling ignores them; they travel with the change directory
through its native lifecycle, including archive.

## Coverage checking before archive

`product-coverage.yaml` is the evidence that promotion later relies on: every requirement a
delivery slice implements must have a coverage mapping (`PRODUCT043` otherwise). Before archiving
an OpenSpec change, run:

```bash
product-definition coverage check
```

Two rules keep the lifecycles independent:

- **Archiving never promotes.** Completing and archiving the OpenSpec change is OpenSpec's
  decision and only OpenSpec's. The product baseline is modified solely by an explicit
  `product-definition change promote`, run by a human, after all slices of the Product Change are
  completed or cancelled and coverage evidence is in place.
- **Handoffs go stale honestly.** If canonical artifacts change while the OpenSpec work is in
  flight, `product-definition handoff status` reports exactly which referenced artifacts changed —
  unrelated repository activity never marks a handoff stale.

## Adoption order

1. **Initialize with the OpenSpec adapter.** `product-definition init --sdd openspec` (add `--ai`
   for AI integrations). Your `openspec/` directory is untouched; what `init` creates is described
   in [Installing into an existing repository](existing-repository.md).
2. **Build the model.** Author the initial baseline with [Define](greenfield.md) for a new
   product, or reconstruct it with [Recover](brownfield.md) for an existing system.
3. **Run the first change through both layers.** Create a Product Change, validate its overlay,
   approve it, slice it, then `product-definition handoff create` targeting a native OpenSpec
   change. Work the OpenSpec change exactly as you always have, maintaining
   `product-coverage.yaml` as tasks complete. Check coverage, archive in OpenSpec, then promote
   the Product Change explicitly.
