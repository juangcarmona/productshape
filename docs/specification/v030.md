# PDaC v0.3 candidate support

The default contract remains v0.2 / `v1alpha1`. Set `version: v1alpha2` in `.product/config.yaml`, or pass `--serialization-version v1alpha2`, to select v0.3 semantics. An explicit selection inconsistent with a configuration file produces `PRODUCT050`. Configuration absence uses the explicitly selected contract.

The authoritative candidate is [spec ec68206](https://github.com/product-definition-as-code/spec/tree/ec68206de270b0d3102ab03a5a9dc9c5785d356a). The versioned schemas ship beside the retained v1alpha1 schemas. The existing frontmatter reference describes v1alpha1; use `prodshape --serialization-version v1alpha2 schema <kind>` for the new field contracts.

## Domain behaviour

Domain Lifecycle (`LC-`) describes a subject term, states and transitions. Its required body sections are Purpose, Invariants, State Semantics, Transition Semantics and Boundaries. Exactly one state is initial; a terminal state cannot be a transition source. State and transition IDs have separate local namespaces.

The lifecycle authors its subject and uses-terms dependencies, plus transition initiated-by, governed-by and realized-by dependencies. Local states and transitions are neither graph nodes nor citation anchors. A Structured Behaviour may cover one lifecycle/transition pair while retaining its required illustrates relationship. Coverage is an authored association, never evidence that a test ran.

Business Rule applies-to accepts Journey and Bounded Context. Use Cases author governed-by; its polarity remains dependency. FR derived-from and QR/Constraint applies-to accept Domain Lifecycle. Only an absent Constraint applies-to field means product-wide scope. An empty list is explicit empty scope.

## Accountable changes and apply

Impact accounting compares the baseline and proposed graph one hop from effective additions, modifications and removals. A byte-identical modification remains a candidate. Repeated occurrences of the same canonical edge produce one cause; different relationships remain separate causes. Dependency target changes question the source; governance changes question either end. Product-wide Constraint changes produce one product-scope cause. Candidates never start another traversal.

The optional unaffected ledger acknowledges each cause with a nonblank reason and content pins. An artifact entry pins the baseline candidate and the current proposed cause (or baseline cause for removal). A product-scope entry has no candidate ID or candidate digest. Invalid entries produce PRODUCT033; unresolved causes produce PRODUCT029 during validation and PRODUCT034 at apply.

Apply gates execute in order: configuration, approved status, document/operation/ overlay validation, baseline drift, acknowledgement validation, unresolved impact. Warnings-as-errors changes the verdict without changing severity. PRODUCT029 is replaced by the apply impact gate. Failed gates emit no affected-citation report.

After gates and filesystem preflight, both dry-run and real apply publish the same prospective citation records before writes. In v1alpha2 JSON, `phase: preflight` identifies this report; process exit zero confirms completion (or successful dry-run). This avoids claiming writes succeeded before they occur. Reports are not persisted. Execution failure attempts to restore every modified byte, deletion and archive move; a rollback failure is reported explicitly. No Git refs or index entries are changed.

## Live citations and evidence

For v1alpha2, default citation verification and apply scan the repository's Markdown and YAML consumers. Product Change completed/rejected/superseded archives are excluded. Apply additionally excludes its own change container and retains other active consumers. Explicit verification targets and provider-specific population views remain available.

`--current-evidence <path>` is repeatable and explicitly adds immutable external evidence documents to the live population for both default citation verification and apply. Other JSON files and historical evidence are never discovered automatically. Evidence records require no companion sidecar. The affected set is the intersection with the effective product diff, ordered by path, location kind and number, target, anchor and prospective status. Occurrences are preserved. Evaluated empty sets report zero. Stale or unresolved downstream citations are information and do not block apply.

Use `prodshape --serialization-version v1alpha2 evidence verify <paths...>` to inspect external runs. The command reports the provider's exact run revision separately from the selected model revision. Passed/failed/inconclusive outcomes remain unchanged when their SB/FR/QR citations become stale. PRODUCT080 stops malformed documents; PRODUCT081 diagnoses duplicate test IDs and disallowed resolved kinds. Duplicate result suppression never renumbers later citation entries. Evidence does not execute tests, manage suites or retries, add product graph edges, or establish an apply gate.

## Migration and qualification

Before selecting v1alpha2, review each BR applies-to UC relationship and move governance to the corresponding UC governed-by field. Preserve the intended product meaning; do not translate unrelated scopes automatically. Review explicitly empty Constraint scopes. Add lifecycles and coverage only where domain behaviour warrants them. Revalidate live Product Changes and author unaffected acknowledgements against current digests. Existing citation pins are not refreshed automatically.

Candidate support is not a release claim. Qualification requires the packaged CLI, the pinned runner and spec fixtures, the retained v0.2 regression suite, and independent tests of pre-write reporting and rollback. See [the implementation plan](../v030-qualification-plan.md).
