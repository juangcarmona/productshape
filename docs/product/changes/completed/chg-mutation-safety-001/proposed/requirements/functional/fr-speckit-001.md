## Requirement

The product MUST integrate with Spec Kit through two mechanisms with distinct ownership.

Citations bind. A Spec Kit feature document that depends on canonical product text MUST carry a citation to every product artifact it derives from, in inline or marker-block form. Citations live in the consumer document and are authored by whoever authors that document; the product side MUST NOT write citations into native Spec Kit files. Citations are verified against the product model through citation verification.

The integration MUST be able to enumerate the consumer documents of a Spec Kit workspace so that verification runs over a known population and zero discovered citations is a set of failures, never a vacuous pass. The enumerated population is the specification, plan and tasks documents of every feature directory. Spec Kit has no archive lifecycle, so every enumerated document is current and the scope-declaration gate applies to all of them: each MUST carry exactly one explicit scope declaration, `pdac-scope: cited` for a bound document that carries at least one citation, or `pdac-scope: none` with a non-empty human-authored reason for an exempt one. Citations alone MUST NOT bind a document. A workspace that is initialized but has no features yet enumerates zero documents.

Managed configuration informs, on Spec Kit's own customization surfaces. The integration's repository writes MUST be limited to: one fully managed guidance file inside Spec Kit's memory directory; a sentinel-delimited managed block merged into each of the workspace's spec, plan and tasks templates, because Spec Kit copies the resolved template into every document it generates, which makes the template the surface where citation must be directed instead of paraphrase; a CI-ready verification example; and ProductShape's own integration metadata. Template merging MUST preserve user-authored template content, MUST be idempotent, and removal MUST strip exactly the managed block. The integration MUST NOT write the constitution, which governs how software is built and never carries product intent (a citation-discipline principle there is the human's to add); it MUST NOT patch Spec Kit's scripts or generated agent command definitions, and it MUST NOT create or edit documents inside feature directories. Spec Kit workspaces are created by Spec Kit's own tooling; the integration requires an existing workspace and never creates one.

The managed template blocks and guidance are steering; the gate is verification. The template blocks MUST NOT themselves contain a parseable citation, scope declaration or drift marker, so a generated document is never classified or cited by an unfilled placeholder: a generated gated document remains unclassified until a human or agent declares it bound and cites, or a human exempts it with a reason.

The managed guidance MUST direct the consumer to start feature specification from a cited context projection rather than paraphrase, to find the impacted product artifacts by comparing the feature's intent with the whole product definition and then widening the result through the product graph, and to record product-definition drift as an explicit warning carrying the machine-readable drift marker, so the drift listing reports it. Drift resolution belongs to humans through the change process; Spec Kit work MUST NOT edit the canonical model.

Every product artifact ID MUST be preserved verbatim across both mechanisms, so that citations and guidance refer to the same IDs the product model uses.

The integration MAY additionally be distributed through Spec Kit's own extension mechanism. Such an extension MUST only provide commands and optional post-phase hooks over the same deterministic operations (cited context projection, citation verification, drift listing); it MUST NOT gain write authority over the product model, MUST NOT alter the verification semantics, and its hooks MUST be optional so a workspace without ProductShape keeps working. The extension is a distribution and in-loop enforcement convenience; the boundary stated above is unchanged by it.

The integration's repository writes are repository mutations and MUST satisfy `BR-MUTATION-001`. Adding, updating and removing the integration MUST each be reportable without performing them, leaving the repository byte-identical, and the report MUST agree with what performing it produces. An operation that reports no changes MUST change no byte: neither the managed guidance file, nor the merged template blocks, nor the installed example, nor the recorded integration metadata. The recorded metadata MUST preserve the moment the integration was first installed across every later add, update and no-op; a separate recorded moment MAY state when managed content last changed, and MUST move only when it did. Recorded metadata that exists but cannot be read, parsed or validated MUST stop the operation and be reported, and MUST NOT be treated as an absent record.

## Rationale

The mutation obligations matter here for a reason specific to this integration: the templates it merges into are files the workspace owns and a human authored. Merging before anyone has seen what the merge would do, or rewriting those templates byte-identically on every invocation, makes the user's own templates unreadable as a record of their decisions. Preserving the first-installation moment is part of the same property — a timestamp that moves on every run records nothing except that the command ran, and it makes every no-op appear in a diff the repository reviews.

BR-SDD-001 and CON-SDD-AGNOSTIC commit the product to framework-agnostic consumption through citations. Spec Kit is the proving second framework: it is structurally unlike OpenSpec (no change-versus-current lifecycle, no enumeration CLI, a per-feature directory layout), so an integration on the same two-mechanism terms demonstrates that the citation contract is framework-neutral rather than shaped around one tool. The population rule exists for the same reason as the OpenSpec one: verification that cannot name the documents it expected can pass by finding nothing. The constitution exclusion keeps the one Spec Kit file that governs engineering principles free of product intent, which is the boundary this product exists to keep visible.
